# SETTWOR site: version history

Every change of the site raises the version. The archive is named `settwor-site-vX.Y.zip`.

## 8.1 (manual theme switch; one Middle request, after the plan was finished; owner's choice)
- Footer, column "Legal": a new group "Colour theme" with three pill buttons, Auto (default, follows the system), Light and Dark (`aria-pressed` shows the chosen one; the filled pill is the chosen one, as for the year tabs). It is hidden until the script runs, so without JS nothing dead is shown.
- The choice is stored in the browser only (`localStorage`, key `settwor-theme`, values `light` or `dark`; Auto removes the key) and set on `<html>` as `data-theme`. A small script in the head of `_layouts/default.html` applies it before the first paint (no flash of the other theme); the code is in a new block at the end of `js/main.js`. The two `theme-color` meta tags (phone browser bar) follow the choice and go back to their system-based values on Auto. Another open tab follows through the `storage` event.
- CSS (`css/main.css`, new block after the system dark block): `[data-theme="dark"]` repeats the dark tokens and the four extra dark rules (logo inverted, TIDAL mark, numbers panel edge, notification icon edge); `[data-theme="light"]` holds the light tokens and, under a dark system, undoes those four rules. The selectors are plain attribute selectors with the same specificity as `:root`, so the reduced transparency and more contrast blocks still win. Two lines for more contrast under each manual theme keep the grey text strong (`--color-text-soft`, `--color-muted`, `--color-line`, `--color-line-soft`). When the system dark block or the base tokens change, change this block too (said in a comment).
- `privacy.html`: one sentence that the theme choice is stored in the browser (local storage) and not sent anywhere.
- Files: `css/main.css`, `js/main.js`, `_layouts/default.html`, `_includes/footer.html`, `privacy.html`, `sw.js` v67, `VERSION`, `CHANGELOG.md`, `AI-NOTES.md`, `todo design.md`, `START-HERE.md`.
- Checked in Chromium on the stub build (430 px; system light and system dark): Auto, Light and Dark change the tokens, the colour scheme, the logo filter and both theme-color tags as intended; the choice survives a reload and is on `<html>` already at DOMContentLoaded; with more contrast the four contrast tokens are right for every combination of system and choice; no JS errors; looked at the footer with Light chosen under a dark system.
- NOT checked: Dark chosen under a light system by eye on every page, 1200 px by eye, real phone (the browser bar colour), Safari (private mode: storage can throw, the code catches it), real Jekyll, live site.

## 3.5 (Apple Design, phase 3, item 3.1: the motion model)
- Decision (plan 3.1): the JS spring is OWN code, about 60 lines, in `js/main.js` section 10 (`window.STW.motion`). No Motion library, no new file, nothing extra to cache or to download. Reason: the site needs one small thing (a spring that can be grabbed), and `main.js` is already cached by `sw.js`.
- Two kinds of motion from now on. (1) Background changes (a card appears, a tab changes): CSS with the tokens `--spring-default` / `--spring-momentum` (already there since 2.8). (2) Things the visitor grabs (release window, lightbox, mobile menu): the JS spring.
- API: `STW.motion.spring({ from, to, velocity, damping, response, onUpdate, onDone })` returns `{ to(next, speed), stop(), value(), velocity() }`. Damping 1.0 by default (no overshoot); response in seconds (not a duration). Re-aiming with `to()` or grabbing with `stop()` keeps the current value and the current speed, so there is no jump. Also `STW.motion.project(v)` (where a throw ends, rate 0.998) and `STW.motion.rubberband(over, size)` (soft edge), both from the skill. `STW.motion.reduced()` tells about reduced motion; with it a spring does not travel, it jumps to the end (the caller adds a short CSS cross-fade, plan 6.1).
- Nothing on the site uses it yet, so nothing looks different. It is used from 3.2 (release window as a sheet).
